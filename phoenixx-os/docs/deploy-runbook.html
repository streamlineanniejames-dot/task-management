How the request travels

Visitor asks for app.phoenixxedu.com

→
Render edge 216.24.57.7 / .15

One Node process SPA + /api/v1

The last box is the whole point. SERVE_WEB=true makes Express serve web/dist alongside the API, so the React app and every /api/v1 call share one origin. That is why there is no CORS configuration, why the chat SSE stream works, and why the subdomain covers the entire product rather than just a front end.

Setting it up again

order matters — each step needs the one before it
1

Add the CNAME at GoDaddy

dcc.godaddy.com → Domains → phoenixxedu.com → DNS → Add New Record

TypeNameValueTTL
CNAME app phoenixx-os.onrender.com 600

The Name field takes app alone — GoDaddy appends the domain itself. TTL 600 while setting up keeps a mistake ten minutes expensive instead of three hours.

2

Claim the domain on Render

dashboard.render.com → phoenixx-os → Settings → Custom Domains

Add app.phoenixxedu.com. Render verifies the CNAME, then issues and auto-renews a certificate. It keeps serving phoenixx-os.onrender.com at the same time, so anything already pointed there — including installed mobile builds — keeps working.

3

Verify from outside

# DNS should show the onrender host as an alias
nslookup app.phoenixxedu.com 8.8.8.8

# 200 and a clean TLS verify means done
curl -s -o /dev/null \
  -w "status=%{http_code} tls=%{ssl_verify_result}\n" \
  https://app.phoenixxedu.com/api/v1/health

tls=0 is a validated certificate. Render's dashboard may still say "issuing" after the certificate is actually live, so trust this over the banner.

Traps

independent hazards, not a sequence
silent

cPanel's Zone Editor is not authoritative

For phoenixxit.com, the SOA primary is ns77.domaincontrol.com — GoDaddy account DNS, not the cPanel box. Records added in cPanel's Zone Editor go to a zone file nothing on the internet queries. No error, no effect.

Edit DNS at dcc.godaddy.com for both domains.

breaks invites

WEB_BASE_URL falls back to localhost

Unset, it defaults to http://localhost:5173 — and that string builds client proposal share links (/p/:token) and team invite links (/accept-invite). Every invite you send would point at the recipient's own machine.

Pinned in render.yaml. Confirm a real invite URL after any service rebuild.

wrong server

Never make app a cPanel subdomain

cPanel's Subdomains tool would create app as a folder on the cPanel box serving static files. The app lives on Render, not there — and the record would fight the CNAME.

The app needs a DNS record only. cPanel should not know it exists.

build-time

The mobile API origin is frozen at build

VITE_API_URL is compiled into the bundle, so a phone already carrying the app keeps calling whatever origin it was built against. Changing the domain does not reach installed apps.

Changing origin means rebuild and reinstall.

may not apply

render.yaml only syncs via Blueprint

If the service was created manually rather than from the Blueprint, Render ignores render.yaml entirely — including the env vars that keep invite links correct.

Then set them by hand under Settings → Environment.

two domains

Two Phoenixx domains, easily confused

phoenixxit.com (ns77/ns78, apex → 107.180.116.47, a GoDaddy cPanel box) hosts the website. phoenixxedu.com (ns17/ns18, apex → 198.12.233.125) carries this app.

Phoenixx OS lives on phoenixxedu.com — deliberate, despite @phoenixxit.com seed accounts.

The instance sleeps after ~15 minutes idle, and the database goes with it. There is no persistent disk on the free plan, so SQLite is rebuilt from the demo seed on every cold start. Anything a user typed is gone. A real domain in front of this reads as a production system to whoever you send the link to.
The service runs in Oregon, not Singapore. render.yaml requests region: singapore, but the live host resolves to gcp-us-west1 — free instances are not offered in every region. From India that is roughly 250 ms of round trip on every API call. Region cannot be changed on an existing Render service; it needs recreating.

The fix for both is one decision. Move to plan: starter and uncomment the disk: block in render.yaml, set DB_FILE=/var/data/phoenixx.db, STORAGE_DIR=/var/data/storage and SEED_ON_BOOT=false, then seed once from the Render shell. Roughly $7/month plus about $0.25/GB. Recreating in Singapore at the same time also removes the latency — at the cost of redoing the DNS step above.

Keep it at one instance. SQLite has a single writer, the chat fan-out is an in-process EventEmitter, and the job runner has no leader election. A second instance would get its own database and its own chat bus — users would silently see different data and miss each other's messages.
