# Deploying Phoenixx OS

The whole product is **one Node process**. It serves the API, the web app, the
chat stream, the background jobs and the generated PDFs, and it keeps its data
in a SQLite file next to itself. That is why deployment is one service and not
four, and it is also the constraint that decides where it can run.

---

## What the host has to provide

| Need | Why | Rules out |
|---|---|---|
| A long-lived process | The job runner is an interval ([`jobs.js`](../server/src/services/jobs.js)) and chat is a held-open SSE connection | Request-scoped serverless functions |
| A writable filesystem | The database is a file; PDFs are written to `STORAGE_DIR` and served back from it | Read-only containers |
| **Exactly one instance** | SQLite has one writer, and the chat fan-out is an in-process `EventEmitter` | Autoscaling to 2+ replicas |
| Node 22.13+ | `node:sqlite` | Older runtimes |

A **persistent disk** is the one thing that is optional — see the two tiers
below. Everything else is non-negotiable until the data layer moves to
Postgres (see *Growing out of this* at the end).

## Free: Render free tier, data resets

Good for a demo link, a client walkthrough or QA. Costs nothing and needs no
card.

The free tier gives you a single instance and no disk, and it sleeps after
about 15 minutes of inactivity. So the deal is:

- **The first request after a sleep takes ~50 seconds** while the instance wakes.
- **The database is thrown away when it sleeps.** `SEED_ON_BOOT=true` notices an
  empty database on the next start and rebuilds the demo workspace, so it always
  comes back as a working app — but anything a tester typed is gone.

That behaviour is deliberate for testing. Do not point real users at it.

**Deploy:**

1. Push this repo to GitHub.
2. Render → **New** → **Blueprint** → pick the repo. It reads
   [`render.yaml`](../render.yaml) and creates the service.
3. Wait for the build. Open the URL and sign in with any demo account
   (`arun@phoenixxit.com` / `Phoenixx@2026` — the full list is in the README).

The JWT secrets are generated by Render on first deploy and then held; you never
see or commit them.

> If Render rejects the blueprint because free instances are not offered in
> `singapore`, change `region:` to `oregon` or `frankfurt`.

## Paid: the same service, with a disk

The moment anyone is entering real data, move up. It is a two-line change to
[`render.yaml`](../render.yaml):

1. `plan: free` → `plan: starter`
2. Uncomment the `disk:` block
3. Set `DB_FILE=/var/data/phoenixx.db`, `STORAGE_DIR=/var/data/storage`,
   `SEED_ON_BOOT=false`

Then seed once, from the Render shell:

```bash
npm run seed
```

Roughly $7/month for the instance plus about $0.25/GB/month for the disk —
confirm current pricing, it moves. The instance no longer sleeps, and the data
survives restarts and deploys.

**Keep the instance count at 1.** Scaling horizontally will corrupt nothing, but
the second instance gets its own SQLite file and its own chat bus, so users
would silently see different data and miss each other's messages.

### Back it up

A disk is not a backup. The database is a single file, so a backup is a copy:

```bash
# from the Render shell, or a cron job shipping it to object storage
sqlite3 /var/data/phoenixx.db ".backup '/var/data/backup-$(date +%F).db'"
```

## Other hosts

Same shape, same constraints.

- **Railway / Fly.io** — attach a volume, keep it at one machine. Fly needs
  `auto_stop_machines = false` or the job runner stops with the machine.
- **A VPS** (Hetzner, DigitalOcean, ~€4–5/month) — cheapest and most control.
  Use the [`Dockerfile`](../Dockerfile) with a volume at `/data`, put Caddy or
  nginx in front for TLS. You own patching and backups.
- **Vercel** — good for the web app alone, but it cannot host this API. See below.

## Configuration

Everything is environment variables; [`.env.example`](../.env.example) lists all
of them. The ones that matter for a deploy:

| Variable | Set it to |
|---|---|
| `NODE_ENV` | `production` |
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | 24+ random characters each. **The app refuses to start in production without them** — the dev fallbacks are in this repo, so anyone could mint a session with them |
| `SERVE_WEB` | `true` — this process also serves `web/dist`, so the whole app is one origin with no CORS to configure |
| `DB_FILE`, `STORAGE_DIR` | Paths on the persistent disk, if there is one |
| `SEED_ON_BOOT` | `true` only on a disk-less free tier |
| `WHATSAPP_PROVIDER`, `EMAIL_PROVIDER` | `log` until you have real credentials; both write to stdout instead of sending |

Generate a secret:

```bash
node -e "console.log(crypto.randomUUID()+crypto.randomUUID())"
```

## Growing out of this

The single-instance design holds comfortably into the hundreds of users. Three
things push past it, in the order you will hit them:

1. **Write contention.** SQLite takes one writer at a time. Long before that
   hurts, you would notice it in slow POSTs under load.
2. **Uptime during deploys.** One instance means a few seconds of downtime on
   every deploy.
3. **Wanting two instances at all** — for redundancy or a rolling deploy.

All three have the same answer: move the data layer to Postgres. Supabase or
Render Postgres both work, and the schema was written to make it a mechanical
translation ([`ARCHITECTURE.md`](ARCHITECTURE.md)). Be honest about the size of
it though — it is not a config change:

- **~1,000 synchronous database calls** across 36 files become `async`, plus 37
  `tx()` blocks. `node:sqlite` is synchronous by design; `pg` is not.
- **The chat fan-out** (`bus` in [`chat.js`](../server/src/services/chat.js))
  becomes Redis or Postgres `LISTEN/NOTIFY`. The call sites do not change — only
  `publish()` and the `/chat/stream` handler touch the emitter.
- **Generated PDFs** move to object storage (S3, R2, Supabase Storage).
- **The job runner** either stays on one designated instance or moves to a
  scheduler with a lock.

Once that is done the API is stateless and Vercel, Cloud Run or any autoscaler
becomes an option. Until then, one box with a disk is not a compromise — it is
the correct shape for the app that exists.
